## Attacks and campaigns

**LiteLLM 1.107.0 supply-chain compromise delivers a boot-time credential stealer and hourly RCE backdoor** — Event date: October 21, 2026 (malicious wheels built 11:20–11:37 UTC; disclosed this afternoon).
The popular Python LLM-gateway package LiteLLM published a trojaned 1.107.0 on PyPI whose wheels drop three files into site-packages: `cook.pth` runs a self-styled "privcollect" stealer whenever *any* Python process starts on the host, harvesting SSH keys, AWS/Azure/gcloud/Kubernetes/Docker credentials, CI/CD secrets (GitLab runner configs, Jenkins master keys, Vault and Terraform tokens), AI dev-tool auth files (Claude Code, Cursor, Copilot, Codex, Gemini CLI), Chromium/Firefox passwords, cross-process environment variables, and the LiteLLM proxy's own provider-key database tables — encrypting everything to `www.litellm[.]dev/healthcheck` under an embedded RSA-4096 key. A second file, `sitecustomize.py`, spawns a daemon that polls a GitHub dead-drop (a `domain.txt` in the `letters9813` repo, now 404) hourly and fetches-and-executes arbitrary Python from a rotating attacker domain. SafeDep's forensics show the sdist's `pyproject.toml` carries an injected maturin `data = "cook"` line present in no public commit, and no public GitHub Actions run built the wheels (which lack provenance attestations) — moderate-to-high confidence the attacker modified the git source feeding BerriAI's private release pipeline. LiteLLM security director Oliver Jensen said the malicious release was pushed "through three engineers' GitHub accounts, appearing to be by way of stolen GitHub CLI OAuth tokens," with one account triggering the project-releaser run and another approving it; all tokens are revoked and all but one user were removed from the GitHub org. Versions 1.106.2, 1.107.0rc1 and 1.107.0rc2 are clean, as are the pinned companions `litellm-proxy-extras 0.4.110` and `litellm-enterprise 0.1.78`.
*Severity:* Not specified by source (supply-chain compromise; no CVSS assigned).
*Why it matters:* LiteLLM sits between applications and every LLM provider, so the stealer's targeted dump of the proxy's credential tables turns one poisoned `pip install` into fleet-wide model/API-key theft — and because the payload hangs off `.pth`/`sitecustomize` hooks, every Python process on the box executes it, not just ones that import litellm. The near-identical `cook.pth` behavior from March's TeamPCP compromise shows the same playbook re-hit the same project seven months later.
*Action:* If 1.107.0 was installed anywhere, treat host and cloud credentials as burned: revoke and rotate from a clean environment and pin 1.106.2 by digest (StepSecurity/vendor guidance).

**Lazarus "FlashHole" uses NIST post-quantum ML-KEM-1024 to shield malware delivery** — Event date: October 21, 2026 (Kaspersky GReAT report; BleepingComputer 4:31 PM ET).
Kaspersky attributes a new Lazarus campaign, dubbed FlashHole, to targets in South Korea, with the standout detail being the operational use of ML-KEM-1024, the NIST-standardized post-quantum key-encapsulation mechanism. LPEClient — the long-running Lazarus tool — receives ML-KEM-1024 public keys from C2 as four 1,568-byte blocks, derives four shared key pairs, returns the ciphertexts to C2 GOST-encrypted via the newer ClientHub loader, and uses the shared secrets to key Threefish decryption of the payload response, which reflectively loads the Cubridge modular backdoor straight into memory. The infection chain starts with spear-phishing to fabricated GitHub Pages CV sites (one hosting an AI-generated portrait, a DreamJob-style lure), pivots through a probable vulnerability in the South Korea-ubiquitous INISAFE CrossWeb EX security plugin, and runs shellcode via the legitimate `fsquirt.exe` binary to install a TechHub downloader fed from private GitHub repositories. Active since at least July 2025; three South Korean organizations (software, construction, wired-communication equipment) are confirmed with more suspected; Kaspersky places FlashHole inside the broader Cascade Hole activity and links it to Operation SyncHole with medium-to-high confidence.
*Severity:* Not specified by source (APT campaign report).
*Why it matters:* This is post-quantum cryptography weaponized in a live delivery chain rather than a proof-of-concept — the group is explicitly hiding later-stage payloads from traffic analysis and "hack now, decrypt later" interdiction, which pushes detection to endpoint telemetry (script/native-binary abuse around CrossWeb EX and `fsquirt.exe`) rather than network inspection.
*Action:* Hunt LPEClient/ClientHub/Cubridge artifacts and CrossWeb EX spawning `fsquirt.exe`; pull Kaspersky's published IOCs for the campaign infrastructure.

## Just missed the window

- **GitLab's scheduled release fixes CVSS 10.0 unauthenticated RCE across 12 years of versions.** GitLab's fourth-Wednesday patch release (19.5.1, 19.4.3, 19.3.6, 19.2.9, 19.1.9, 19.0.10, 18.11.13) shipped October 21 hours before this window opened (vendor cadence plus a pre-noon threat brief carrying the CVE; The Hacker News covered it at ~3 PM ET). CVE-2026-110264 is an integer overflow in the bundled Onigmo regex compiler enabling unauthenticated RCE on self-managed instances of every release back to 7.0 (2014) — and admins who applied the October 12 CVE-2026-97229 emergency patches are back in range, since those fixes stopped at 19.2. GitLab shipped four out-of-SLA backports, sees no exploitation, and published two Sigma detection rules ("Onigmo native worker crash," "Org mode render error burst"); no interim workaround exists — upgrade is the only mitigation, with DB-migration downtime on single-node for 19.4.3/19.3.6. Same release fixes CVE-2026-15723 (8.2 High, SAML+LDAP auto-link account takeover) and CVE-2026-112212 (7.5 High, OAuth/OIDC discovery cache poisoning). Sources: GitLab patch release notes, Oct 21, 2026 — https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/ ; The Hacker News, Oct 21, 2026 — https://thehackernews.com/2026/10/critical-gitlab-flaw-cvss-100-could.html
