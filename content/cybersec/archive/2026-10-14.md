**Microsoft's biggest Patch Tuesday ever: 1,400+ flaws, one exploited zero-day, two disclosed zero-days** — Event date: October 13 (Patch Tuesday)
Microsoft shipped security updates on October 13 fixing a record 1,411 flaws counted by BleepingComputer's methodology (1,413 total including 348 Azure/Exchange/other fixes Microsoft released earlier in the month, per The Hacker News, CrowdStrike and SecurityWeek), 70 of them rated Critical — 57 of those RCE. The actively exploited zero-day is CVE-2026-96951, a Windows Shell command-injection flaw used to bypass the Mark-of-the-Web security feature; Microsoft shared no exploitation details, and CISA added it to the KEV Catalog on October 13 (federal remediation deadline October 16). The two publicly disclosed zero-days are CVE-2026-108398 (.NET Framework untrusted-search-path flaw that bypasses Windows Defender Application Control, found by Google Project Zero's James Forshaw) and CVE-2026-92707 (MessagePack-CSharp denial of service). Microsoft also introduced an experimental "risk cohorts" model — 15 groups mapping related flaws (e.g., 136 in filesystems/storage/backup, 135 in Office documents and mail clients) to help prioritize this record backlog.
- Severity as published: 70 Critical per Microsoft; CVSS for CVE-2026-96951 not specified by source.
- **Why it matters:** AI-accelerated bug hunting is now visibly inflating patch volume ("hundreds of CVEs in a single release used to be the exception," said ZDI's Dustin Childs), which breaks triage-by-CVSS workflows — prioritization, not blanket deployment, is the scarce skill, and Microsoft's own cohort experiment is an admission of that.
- **Action:** Deploy the October updates now, led by the exploited Windows Shell zero-day; plan around Windows 11 24H2 Home/Pro and Windows 10 Enterprise LTSB 2016, which reached end of updates with this release. Note Microsoft's known issues this cycle: non-admin Remote Desktop connections can fail when "Administrator protection" is enabled (confirmed Oct 14), and the September-caused Always On VPN bug was fixed Oct 14.

**CISA orders immediate Ivanti Connect Secure updates as exploited zero-day chains to root** — Event dates: Ivanti advisory + KEV listing Oct 13; CISA emergency guidance Oct 14
CVE-2026-104935 (CVSS 8.6, High) is an unauthenticated authentication bypass in Ivanti Connect Secure (versions 25.1.1.1 and prior, 25.1.2.2 and prior, 22.8R2.4 and prior) allowing remote, low-complexity command execution without user interaction. Ivanti fixed it on Tuesday in builds 22.8R2.5 / 25.1.1.2 / 25.1.3.0 / 25.1.3.1, warning of "limited exploitation in the wild"; Defursed… (Defused) confirmed in-the-wild abuse from October 1, and honeypots logged 105 exploit attempts per The Hacker News. Volexity reports actor UTA0576 chained the bypass and an RCE (both tracked as CVE-2026-104935) with a still-unpatched privilege-escalation flaw to get root on a fully patched 22.8R2.4 appliance beginning October 3, then harvested Active Directory credentials and secrets — including LAPS passwords and BitLocker recovery keys. CISA added the flaw to KEV on October 13 (FCEB deadline October 16 under BOD 26-04) and separately urged all organizations to update immediately; Shadowserver tracks 5,600+ internet-exposed ICS-fingerprinted hosts. CISA warns Ivanti's Integrity Checker Tool may not detect exploitation because the actor's commands run in memory.
- Severity as published: CVSS 8.6 High (The Hacker News); High (Ivanti advisory via BleepingComputer).
- **Why it matters:** This is Ivanti's 36th KEV entry since November 2021 — the pattern of edge-VPN appliances as initial access persists despite years of burn, and the post-exploitation focus on LAPS/BitLocker secrets turns one box into domain-wide credential material.
- **Action:** Patch immediately; for any appliance that was exposed while unpatched, treat as potentially compromised: CISA prescribes config backup → factory reset and upgrade (rebuild virtual instances) → restore → reset all domain/admin/local passwords, revoke/reissue stored certificates, reset API keys and license-server credentials — with network/memory forensics, not ICT alone.

**SAP discloses CVSS 10.0 OAuth2 SSRF in Cloud SDK for Python; six later releases still incomplete** — Event date: October 13 (SAP security advisory)
CVE-2026-89111 lets an attacker who controls the tenant_subdomain parameter of a multi-tenant SAP BTP application redirect its OAuth2 token request to a server they control, exfiltrating the application's client ID and secret. SAP's advisory (October 13) names version 0.45.2 — released August 21 — as the fix, and the advisory is tracked under GHSA-4mv3-jxxm-9cx2. The Hacker News found that six later SDK releases (0.53.0–0.55.0) don't apply the tenant-subdomain validation in every code path, notably Destination calls.
- Severity as published: SAP CVSS 10.0 (maximum).
- **Why it matters:** A perfect-score flaw that leaks machine-identity credentials undermines the trust boundary of an entire SaaS estate — the stolen OAuth2 client secret is a pass into BTP services without any user factor.
- **Action:** Upgrade Cloud SDK for Python to 0.45.2+ (verify the subdomain check holds in your SDK line — 0.53.0–0.55.0 regressions reported) and rotate BTP OAuth2 client credentials wherever tenant names are attacker-influenceable.

**curl 8.23.0 fixes High-severity HTTP/2 upload use-after-free with demonstrated client-side code execution** — Event date: October 14 (curl 8.23.0 release + advisory)
CVE-2026-92392 stems from curl mishandling an HTTP/2 RST_STREAM during uploads: the server stalls the transfer, resets the stream, and curl's retry/flush path frees an easy handle while a stale pointer remains reachable — server-supplied data can then overwrite a function pointer. Affects curl/libcurl 8.12.0 through 8.22.0 (shipped since February 2025). The reporter's PoC achieved code execution, but exploitation needs exact target build/heap knowledge and a ~23-byte payload window — curl rated it High (its first High since 2023) expecting real attacks to end in crashes; no in-the-wild use reported. The 8.23.0 release fixes 24 CVEs total (the other 23 Low); fixes are backported on 8.14.3 / 8.16.2 / 8.20.2 branches, with Debian trixie shipping DSA-6558-1. The finding is credited to "Luna with Claude, Anthropic" (Luna Tong, via Anthropic's OSS Scanner).
- Severity as published: High (curl project's four-level scale; no CVSS — NVD had not analyzed as of Oct 14).
- **Why it matters:** curl is the internet's default transfer layer — a client-side flaw flips the trust model (the server attacks the client), and another AI-driven discovery landing in widely deployed infrastructure confirms the tooling shift in vulnerability research.
- **Action:** Upgrade to curl/libcurl 8.23.0 (or branch equivalents); where you can't, force HTTP/1.1 (--http1.1 / CURLOPT_HTTP_VERSION) or use builds without HTTP/2 support.

**Critical Ghostscript flaw lets crafted PDFs trigger unauthenticated RCE (CVE-2026-39919)** — Event date: October 13 (Wordfence/Defiant disclosure reported)
A heap buffer overflow in Ghostscript's JPEG 2000 decoding — mishandled low-bit-depth samples and component resolutions — lets a crafted PDF force a 1,024-byte write into a 256-byte buffer. Wordfence built two exploits and demonstrated unauthenticated RCE on a test server via the WordPress → Imagick → ImageMagick → Ghostscript thumbnail chain; the flaw affects any online system rendering attacker-supplied PDFs, Ghostscript 9.21 through 10.07.1 (all ten tested Linux environments contained the vulnerable code). Artifex fixed it on September 8 in 10.08.0, with backports; no in-the-wild exploitation observed.
- Severity as published: Critical (per BleepingComputer/Wordfence reporting); CVSS not specified by source.
- **Why it matters:** PDF rendering is a universal, pre-auth server code path (upload → preview/thumbnail), so exploitation surfaces are far broader than WordPress — any document pipeline with ImageMagick in the middle inherits this.
- **Action:** Ensure Ghostscript ≥ 10.08.0 (check backport revisions); rebuild container base images; where upgrade is impossible, block PDF uploads or disable PDF rendering policies in ImageMagick.

**Global disruption dismantles the Chinese-language phishing ecosystem behind 1 billion+ messages** — Event date: October 14 (Microsoft report and coordinated takedown)

**Hirudo Android banking trojan ships patched versions of real banking apps** — Event date: October 14 (ThreatFabric disclosure and coverage)
ThreatFabric's new Android RAT replaces legitimate banking apps with modified builds — it identified drop-ins for eight Indonesian banks — in which the apps' own security checks are disabled, stealing credentials from inside the trusted binary. Delivered through shopping, adult-video and entertainment dropper apps carrying the trojan as a separate install package, Hirudo combines on-device credential theft, live remote control, screen and camera capture, and SMS theft with a "fairly mature backend"; credential targeting spans Indonesia, China, India, Mexico, Morocco and Thailand.
- **Why it matters:** Patching the bank's own app defeats client-side fraud controls and app-attestation assumptions wholesale — as ThreatFabric's EVP framed it, this is an escalation in financial fraud where the malicious code runs *as* the trusted app.
- **Action:** For banks/regulated apps: move integrity verification server-side and monitor for signature/attestation anomalies; for enterprises/mobile teams: enforce managed-device app stores and block unknown-source installs for work profiles.

**GitHub forces unvalidated npm trusted-publishing configs to expire after 48 hours** — Event dates: GitHub change live October 2 (changelog); flaw disclosure reported October 13
Researchers found that npm trusted publishing could be abused to push new versions of other users' packages without stealing credentials, by reclaiming a changed repository/project name before the binding was validated — exposing 1,500+ packages with 10M+ cumulative downloads and 1M+ monthly downloads. GitHub's mitigation: unvalidated trusted-publisher configurations now expire 48 hours after creation (validated on first successful publish), identity changes require a fresh trust relationship, and npm now rejects trusted-publishing tokens from GitHub Actions issue_comment events on top of the existing pull_request_target restriction.
- **Why it matters:** CI-native publishing replaced the credential-theft step in supply-chain attacks with identity-confusion, and 10M-download packages were one neglected config away from hijack — this is the npm-wormhole class the SolarWinds-to-xz lineage keeps exploiting.
- **Action:** Audit your packages' trusted-publisher configurations for stale/renamed linked repos, re-validate after any repository or project identity change, and alert on publish events from unexpected pipelines.
