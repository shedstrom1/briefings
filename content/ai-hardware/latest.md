## AI hardware and silicon

**Intel Razor Lake-AX: 96 GB MoP and 192 GB MoB variants detailed** — Event date: 2026-11-27 (05:27 EST)
A follow-up to yesterday's prototype leak now describes two product lines. Jaykihn reports the Memory-on-Package line officially tops out at 96 GB (128 GB unofficially), while a Memory-on-Motherboard line supports up to 192 GB (256 GB unofficial), built around the 8P+16E+4LPE / 32-Xe3-core configuration. The chip is said to expose 16 PCIe 5.0 plus 8 PCIe 4.0 lanes and four DMI 5.0 lanes. VideoCardz frames the large-memory, high-I/O combination as a plausible alternative to AMD's Halo processors for compact workstations and local AI; production is listed for Q3 2027. Treat as a pre-announcement rumor from a single leaker, not a confirmed spec. **Why it matters:** if the 192 GB MoB tier ships, it puts Halo-class unified memory into a socketed, upgradeable desktop form factor — directly relevant to anyone sizing a box for 100 GB+ local models. **Local inference:** targets 96–192 GB unified-memory compact workstations; no VRAM class or price confirmed, and availability is not until 2027. **Source:** VideoCardz, "Intel Razor Lake-AX reportedly features two variants: 96GB MoP and 192GB MoB," 2026-11-27 10:27 GMT — https://videocardz.com/newz/intel-razor-lake-ax-reportedly-features-two-variants-96gb-mop-and-192gb-mob

**AMD submits RDNA 5 (GFX13) driver support for Linux 7.5** — Event date: 2026-11-27 (04:15 EST)
A November 26 DRM-Next pull request adds early support for Graphics Core 13 (GC13), the Graphics Memory Controller (GMC 13), SDMA 8, SoC v2 and Display Core Next 6 — the hardware blocks expected in AMD's RDNA 5 GPUs. AMD has also started GFX13 work in Mesa's RadeonSI OpenGL and RADV Vulkan drivers, so kernel and userspace development are both underway. Linux 7.5 is expected to reach stable in Q1 2027, and first RDNA 5 products are rumored for H2 2027. **Why it matters:** AMD's ROCm/local-inference path on Linux depends on kernel and Mesa enabling landing ahead of silicon; this is the earliest concrete driver signal for the generation after RDNA 4. **Local inference:** no shipping hardware or VRAM class yet — this is driver plumbing for 2027 Radeon GPUs. **Source:** VideoCardz, "AMD RDNA 5 graphics support is coming to Linux 7.5," 2026-11-27 09:15 GMT — https://videocardz.com/newz/amd-rdna-5-graphics-support-is-coming-to-linux-7-5

## Inference software and benchmarks

**llama.cpp moves FP8/NVFP4 quant scales into GGML (#28898)** — Event date: 2026-11-27 (08:51 EST)
The largest merge of the window: scale tensors are now stored in a map tied to their weights and applied automatically in `build_lora_mm`, making `MUL_MAT`/`MUL_MAT_ID` backward compatible while allowing direct conversion of many FP8/NVFP4 safetensors models hosted on Hugging Face. The CUDA backend folds the scale into existing epilogue multiply fusions with no performance loss; other backends reject scaled ops until they add support. The change is 2,906 additions / 2,412 deletions across 224 files and was merged at 13:51:55Z — about two minutes before the window closed. **Why it matters:** it removes a conversion step that has kept many FP8/NVFP4 checkpoints out of llama.cpp, widening the set of models that run locally on consumer GPUs. **Local inference:** benefits CUDA cards most directly (epilogue-scale fusion); other backends (Vulkan/Metal/SYCL) need their own support before they see the benefit. **Source:** llama.cpp PR #28898, merged 2026-11-27 13:51:55Z — https://github.com/ggml-org/llama.cpp/pull/28898

**llama.cpp lets MoE-cache experts run on a different backend (#33133)** — Event date: 2026-11-27 (04:32 EST)
A multi-GPU fix for `inkling2_loop` layer splits: the MoE cache copy callback previously asserted when the router selected experts on a different device than the loop pass. The patch stores per-layer experts in `build_lookup` and derives token count from the copied ids, so a layer split across a GPU and an RPC/second device produces greedy output identical to all-experts-on-GPU. Author tested it with Inkling-2-Mini IQ4_NL, `-cmoe --moe-cache-mib 2048`, on one RTX PRO 6000 plus a `ggml-rpc-server` second device. **Why it matters:** it makes CPU/RPC expert offload actually usable for looped MoE models like Inkling 2 Mini, which is how large MoEs get squeezed onto modest VRAM. **Local inference:** validated on RTX PRO 6000 + RPC second device; enables multi-GPU and GPU-plus-RAM expert splits. **Source:** llama.cpp PR #33133, merged 2026-11-27 09:32:07Z — https://github.com/ggml-org/llama.cpp/pull/33133
