**SGLang (Saturday): exact per-row speculative sampling penalties in verify (#52054) — EAGLE/NGRAM/DFlash/DSpark exactness.** Event date: 2026-11-21. Follow-up to #52035: verify rows of the same request no longer all receive the same penalty — each row now counts the history counts plus its own ancestor draft tokens, and min_new_tokens is gated by lens + depth. The new sampling.verify_penalties kernel (JIT, CUDA sm_80+) replaces the batch-level penalties with exact per-row values across EAGLE trees, NGRAM, DFlash and DSpark, with bitwise equality to non-spec decoding on the rows (fp32 table math, one round to the logits dtype).
Why it matters: per-row exactness is the kind of correctness fix that, once merged, makes EAGLE- and DSpark-verified agentic decoding trustworthy on long chains — and the bitwise check gives it a crisp verification story.
Local inference: CUDA sm_80+; benefits any DSpark/EAGLE serving workload on GeForce-class and datacenter GPUs.
Source: SGLang PR #52054 — GitHub, merged 2026-11-21 22:28 UTC — https://github.com/sgl-project/sglang/pull/52054

**SGLang (Saturday): deep_select multi-wave cluster top-k for long-tailed rows (#51348).** Event date: 2026-11-21. Opt-in via SGLANG_DEEP_SELECT_MULTIWAVE=1: bf16 top-k batches with more rows than every one-wave tier (and at most 512 rows) now route to the cluster tier with the most rows per wave — e.g. the 2-CTA tier on SM107 — and run over several waves instead of sending all rows to a one-CTA-per-row kernel whose time is set by the longest row. On Vera Rubin (SM107, 212 SMs), a 40-request DSpark batch with 240 rows per index layer (top-512 over 240 rows per decode step) was forced onto the one-CTA-per-row path, which sized itself by the longest row in the batch (~2.6–6.3× the mean); routing the same batch as multi-wave follows the total row length instead of the longest row. Off by default (uniform-row workloads still favor the one-CTA kernel).
Why it matters: a heuristic that made the slowest request in the batch determine every row's latency is exactly the failure mode that wrecks agentic workloads on Rubin; this fix turns it into a workload-aware knob.
Local inference: Vera Rubin (SM107) and any GPU running bf16 top-k at >512 rows; off by default; benefits DSpark/EAGLE batched decode.
Source: SGLang PR #51348 — GitHub, merged 2026-11-21 21:00 UTC — https://github.com/sgl-project/sglang/pull/51348

**TensorRT-LLM (Saturday): QSA PrimTS indexer scorer 1.5–1.65× faster on Rubin decode (#21825).** Event date: 2026-11-21. Rubin ts3, CUDA-graph replay medians, 256 MiB L2 scrub, page 32, compress 4, rebased onto main c5327e53. MMA transposed to S^T = K-bar × Q^T, so a TMEM lane holds one block's scores for all rows with the four head columns adjacent, and the head sum is three register adds with coalesced 128 B score stores. Decode (rows ≤ 4 × requests) uses a 4-row tile, 4 KB of Q, 32 TMEM columns, 6-stage K ring and 4 epilogue warps; prefill keeps the 32-row tile. Benchmarks: prefill 1.11–1.34× (512 rows 1.11×, 16384 rows 1.34×), decode 1.56–1.65× (1 row 1.56×, 256 rows 1.56×, 2048 rows 1.61×). 1.5–1.65× at 32K context with 4 requests; the remaining cost is per-CTA ring fill/drain at one CTA per SM.
Why it matters: the Rubin NVFP4 decode path was already in the docs; this is the number that moves decode throughput, and 1.5× is the kind of delta that changes whether the next generation of NVFP4 decoders is viable on one Rubin card.
Local inference: Vera Rubin (SM107); Hopper/SM100 unchanged for decode.
Source: TensorRT-LLM PR #21825 — GitHub, merged 2026-11-21 21:03 UTC — https://github.com/NVIDIA/TensorRT-LLM/pull/21825

**SGLang (Saturday): Mega-mHC prefill dispatch on gfx950 (#44265).** Event date: 2026-11-21. On gfx950 the SGLANG_OPT_DSV41_MEGA_MHC_PREFILL flag did nothing — the fused HIP mHC boundary (hc_boundary_fused) owned the seam and the DeepSeek-V4.1-Flash prefill never called aiter's flydsl_mega_mhc. Requires an aiter build exposing aiter.ops.flydsl.flydsl_mega_mhc (ROCm/aiter #6179, merged as 31aef274); rocm/sgl-dev images from 20261018 already include aiter 2bb5491.
Why it matters: the same optimizer that made the SM100 path fast now reaches MI355X/gfx950 — DeepSeek-V4.1 prefill on AMD is the kind of workload that has been lagging NVIDIA; this is the first day-0 ROCm win.
Local inference: MI355X/gfx950-class AMD; opt-in env flag.
